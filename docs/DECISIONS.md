# Журнал архитектурных решений (ADR)

Каждая запись фиксирует одно решение: контекст, само решение, отвергнутые
альтернативы, последствия. Решения не удаляются и не переписываются;
если решение пересматривается, заводится новый ADR со ссылкой на старый.

Формат:

```
## ADR-NNN — YYYY-MM-DD. Краткая формулировка решения

### Контекст
Почему понадобилось решать. Что было до.

### Решение
Что именно решили.

### Альтернативы
Что рассматривали и почему не выбрали.

### Последствия
Что меняется в коде, в процессе, в документации.
```

## ADR-001 — 2025-XX-XX. Слоистая архитектура с FSMService

### Контекст

В кодовой базе одновременно существовали три разных дизайна
оркестрации, написанных разными итерациями AI без единого замысла:
- `application/use_cases/` — async use cases (по одному классу на действие).
- `domain/commands.py` + `domain/session.py` — Pydantic-агрегат `Session`
  с методом `apply_command`.
- `application/fsm_service.py` — `FSMService` с возвратом эффектов как данных.

Дублирование запутывало и блокировало развитие.

### Решение

Принят единый стиль:
- `domain/` — чистая FSM (states, events, transitions, context).
- `application/` — синхронный оркестратор FSMService.
- `infrastructure/` — async-адаптеры.
- `composition/` — сборка приложения.

Старые альтернативные реализации удаляются.

### Альтернативы

- **Clean Architecture с use_cases.** Отвергнуто: для FSM из ~15 событий
  получается 15 классов use case с одинаковой логикой
  «команда → событие → переход». Дублирование без пользы.
- **Pydantic-агрегат Session с apply_command.** Отвергнуто: мешает
  невалидируемые состояния (агрегат должен валидироваться при создании,
  но FSM требует промежуточных состояний).
- **Гибрид FSMService + use_cases.** Отвергнуто как два слоя оркестрации
  без чёткого распределения ответственности.

### Последствия

- Удаляются: `application/use_cases/`, `application/ports.py`,
  `domain/session.py`, `domain/commands.py`, `adapters/db/repositories.py`,
  `domain/repositories.py`, пустые заготовки `ai_tutor/`, `api/`,
  `core/`, `services/`.
- Async-код только в `infrastructure/`.
- Тесты `application/` не требуют моков async-ресурсов.

## ADR-002 — 2025-XX-XX. Эффекты как данные

### Контекст

FSMService должен делать побочные эффекты (сохранить сессию, отправить
сообщение, вызвать LLM, очистить контекст). Прямой вызов из синхронного
кода невозможен (LLM-клиент async) и затрудняет тестирование.

### Решение

`FSMService.handle(command, ctx, state)` возвращает кортеж:
`(new_state, new_ctx, list[Effect])`.

`Effect` — структура данных (dataclass). Исполнение эффектов —
обязанность infrastructure-адаптера, который вызвал FSMService.

### Альтернативы

- **Прямой вызов адаптеров из FSMService.** Отвергнуто: смешивает
  синхронный домен и async-инфраструктуру.
- **FSMService как async с inject зависимостей.** Отвергнуто: усложняет
  тестирование, требует моков, async без реальной необходимости.

### Последствия

- Тесты FSMService проверяют эффекты как обычные данные.
- Адаптеры решают, как исполнять эффекты (синхронно/асинхронно,
  параллельно, с retry).
- Сложные сценарии (многошаговое исполнение эффектов с возвратом
  результата в FSM) оформятся на Срезе 3.

## ADR-003 — 2026-XX-XX. Вертикальные срезы вместо большого проектирования

### Контекст

Перед нами стоит задача MVP с большим объёмом: FSM, persistence, LLM,
TTS/STT, два web-интерфейса, админка, деплой. Полное проектирование
«на бумаге» до начала кодинга заняло бы несколько сессий и накопило
бы большое количество непроверенных предположений.

В предыдущих итерациях AI уже попадал в эту ловушку: спроектировал
сразу много и в разных стилях, без обратной связи от рабочего кода.

### Решение

Реализация идёт **вертикальными срезами**, описанными в `ROADMAP.md`.
На каждом срезе:
- система работает целиком (для своего уровня);
- покрытие тестами 100% по бизнес-логике слоя;
- документация обновляется до перехода к следующему срезу.

Перед каждым срезом — короткое уточнение деталей. Документы по
конкретным темам (DOMAIN, API, DATA) появляются по мере того, как
они становятся актуальными.

### Альтернативы

- **«Сначала весь скелет».** Отвергнуто: высокий риск переделок,
  длинная фаза без рабочего кода, накопление неверных предположений.

### Последствия

- На раннем этапе документация неполна — это нормально.
- Возможны переделки внутри срезов при обнаружении ошибочных предположений.
- Каждый срез завершается рабочей системой, которую можно показать
  и протестировать.
- Расширение MVP (новые фичи) делается через новые срезы или через
  изменения внутри существующих, с фиксацией в этом журнале.

## ADR-007 — 2026-XX-XX. Срез 1, Коммит 0 — чистка наследия

### Контекст

При попытке двигаться дальше по ROADMAP (TRAINING_QUIZ, EXAMPLE и т.д.)
обнаружено, что в кодовой базе всё ещё живут артефакты из ранних
итераций, которые ADR-001 предписывал удалить:

- `src/domain/commands.py` — конкурирующий набор команд с текстовыми
  полями (`SubmitAnswer(text)`, `SubmitDialogTurn(text)`),
  нарушающий ADR-004 (команды-факты).
- `src/domain/effects.py` — конкурирующий набор эффектов с другой
  сигнатурой `EmitMessage(template_key, params)`, нарушающий
  ADR-001 (эффекты живут в `application/`).

Кроме того, тесты в `tests/unit/application/` физически не запускались:
они конструируют `SessionContext()` без аргументов и ожидают поле
`has_active_session`, которого в dataclass'е не было. То есть слой
`application/` был покрыт тестами на бумаге, но фактически — нет.

### Решение

Перед началом работы над следующим коммитом Среза 1 проводится
консолидирующая чистка:

1. Удаляются `src/domain/commands.py` и `src/domain/effects.py`
   (исполнение ADR-001 с опозданием).
2. В `SessionContext` добавляется `has_active_session: bool = False`,
   а поля `employee_name` и `product_id` получают дефолт `""`.
   Это легализует вызов `SessionContext()` в тестах INIT/RESUME,
   где данных пользователя ещё нет.
3. В `tests/unit/test_transitions.py` добавляется инвариант
   `test_every_event_is_used`, фиксирующий полноту таблицы переходов
   относительно перечисления `FSMEvent`.

### Альтернативы

- **Сделать `employee_name`/`product_id` обязательными и переписать
  тесты на фабрику `make_ctx(...)`.** Отвергнуто: на стадии INIT эти
  данные физически отсутствуют (пользователь их ещё не ввёл), и
  «обязательность» создавала бы фейковые значения вроде `"unknown"`,
  засоряя модель. Бизнес-валидация имени/продукта — задача стадии
  MENU, не доменного контекста.
- **Оставить дубликаты с `# legacy` и постепенно мигрировать.**
  Отвергнуто: пока есть два контракта — следующий коммит легко
  упрётся в неоднозначность, какой из них использовать.

### Последствия

- ADR-001 наконец исполнен полностью.
- Тесты `application/` запускаются и зеленеют.
- Появляется автоматический контроль полноты `TRANSITIONS` — добавление
  нового события в `FSMEvent` без подключения к таблице падает в CI.
- Открыт путь к Срезу 1, Коммиту 1: блок TRAINING_QUIZ (`SubmitQuizAnswer`,
  `ExplanationDone`, мутации `quiz_question_index` и `last_answer_correct`).

## ADR-007 — 2026-XX-XX. Срез 1, Коммит 0 — чистка наследия и контракт FSMResult

### Контекст

При попытке двигаться дальше по ROADMAP (TRAINING_QUIZ и т.д.)
обнаружены три проблемы, блокирующие движение:

1. В `src/domain/` всё ещё живут `commands.py` и `effects.py` —
   конкурирующие контракты, нарушающие ADR-001 и ADR-004 (текстовые
   команды `SubmitAnswer(text)` вместо команд-фактов).
2. Тесты `application/` физически не запускались: они конструируют
   `SessionContext()` без аргументов и опираются на поле
   `has_active_session`, которого в dataclass'е нет.
3. `FSMResult` возвращает только `(new_state, effects)`, без `new_ctx`.
   ADR-002 и ARCHITECTURE.md фиксируют тройной контракт
   `(new_state, new_ctx, effects)`. Без `new_ctx` следующий коммит
   (TRAINING_QUIZ) не сможет инкрементировать `quiz_question_index`
   и записывать `last_answer_correct`.

### Решение

Перед началом работ над TRAINING-блоком проводится консолидирующий
коммит «Срез 1, Коммит 0»:

1. Удаляются `src/domain/commands.py` и `src/domain/effects.py`
   (исполнение ADR-001 с опозданием).
2. В `SessionContext` поля `employee_name` и `product_id` получают
   дефолт `""`, добавляется `has_active_session: bool = False`.
   Это легализует вызов `SessionContext()` в тестах INIT/RESUME,
   где данных пользователя ещё нет.
3. `FSMResult` расширяется до тройки `(new_state, new_ctx, effects)`.
   Сигнатура `FSMService.handle` остаётся `(state, command, ctx)` —
   расхождение с ARCHITECTURE.md зафиксировано: документ будет
   приведён в соответствие с кодом (state-first читается естественнее
   как «получатель команды»).
4. В `tests/unit/test_transitions.py` добавляется инвариант
   `test_every_event_is_used`, фиксирующий полноту таблицы переходов
   относительно `FSMEvent`. RESUME_CONFIRMED явно занесён в
   `EVENTS_HANDLED_OUTSIDE_TABLE`.

В Коммите 0 `new_ctx is ctx` во всех текущих хелперах — мутации
контекста начнутся в Коммите 1 (TRAINING).

### Альтернативы

- **Сделать `employee_name`/`product_id` обязательными.** Отвергнуто:
  на стадии INIT эти данные физически отсутствуют, обязательность
  потребовала бы фейковых значений вроде `"unknown"`.
- **Оставить старые `commands.py`/`effects.py` с пометкой `# legacy`.**
  Отвергнуто: сосуществование двух контрактов гарантированно даст
  путаницу в Коммите 1.
- **Сделать `handle(command, ctx, state)` (как в ARCHITECTURE.md).**
  Отвергнуто после согласования: `(state, command, ctx)` читается
  естественнее, документ будет приведён к коду.

### Последствия

- ADR-001 исполнен полностью.
- Тесты `application/` запускаются и зеленеют.
- Появляется автоматический контроль полноты `TRANSITIONS`.
- Контракт `FSMResult` готов к мутациям контекста — Коммит 1
  ложится без рефакторинга.
- `docs/ARCHITECTURE.md` подлежит обновлению: сигнатура `handle`,
  тройка `(new_state, new_ctx, effects)`.

## ADR-008 — 2026-XX-XX. MAX_ATTEMPTS как мёртвый переход в Срезе 1

### Контекст

В `domain/events.py` определено событие `MAX_ATTEMPTS` — «принудительное
завершение TRAINING_QUIZ». В `TRANSITIONS` для него заведён переход
`TRAINING_QUIZ + MAX_ATTEMPTS → TRAINING_DONE`.

Однако при анализе бизнес-требований обнаружено: в текущем сценарии
TRAINING_QUIZ имеет цикл «вопрос → разбор → тот же или новый вопрос»
без верхнего лимита попыток. Сотрудник продолжает отвечать, пока
не пройдёт все 3 вопроса корректно. Лимит попыток на квиз — фича,
которая может появиться в будущих итерациях (анти-зацикливание),
но в Срезе 1 не имеет источника эмиссии.

Если ввести логику «после N попыток эмитим MAX_ATTEMPTS» прямо
сейчас, придётся:
- определить, что такое N (3? 10? настраиваемо?);
- ввести в `SessionContext` счётчик попыток;
- решить, что считать «попыткой» — каждый вопрос или весь квиз.

Все три решения требуют продуктового ввода, которого сейчас нет.

### Решение

В Коммите 1 (Срез 1) `MAX_ATTEMPTS`:
- остаётся в `FSMEvent` и в `TRANSITIONS` (структурная полнота);
- **не эмитится** ни одной командой;
- покрывается тестом `test_undefined_event_in_quiz_does_not_emit_max_attempts`,
  фиксирующим текущую семантику.

`test_every_event_is_used` (введён в Коммите 0) проходит, потому
что событие присутствует в `TRANSITIONS`.

Когда продуктовое требование «защитный стоп-кран на квизе» придёт,
этот ADR будет заменён на конкретный механизм эмиссии.

### Альтернативы

- **Удалить `MAX_ATTEMPTS` из enum и таблицы.** Отвергнуто: тогда
  при возврате фичи придётся менять FSMEvent, мигрировать `saved_state`
  в БД и т.п. Дешевле оставить структурно.
- **Эмитить `MAX_ATTEMPTS` после N=3 неверных ответов подряд.**
  Отвергнуто: «N=3» — придумано из воздуха, без источника требования.

### Последствия

- В Срезе 1 квиз не имеет верхней границы по попыткам.
- Защита от UI-зацикливания (если такая нужна) делается на уровне
  адаптера, а не FSM.
- При возврате фичи — заменить этот ADR, добавить механизм эмиссии,
  обновить `FSM_INVARIANTS.md`.
