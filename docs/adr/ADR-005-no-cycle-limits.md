# ADR-005: Петля ремедиации без лимитов

* **Статус:** Принято
* **Дата:** 2025-04-27
* **Контекст:** Срез 1, проектирование цикла EXAMPLE → PRACTICE → KNOWLEDGE.

## Контекст

Бизнес-логика тренажёра допускает повторные циклы ремедиации:

```text
EXAMPLE → PRACTICE → PRACTICE_EVAL
           │              │
           │              ├─ ALL_ZONES_OK    → PRACTICE_SUCCESS → FINISH
           │              └─ HAS_FAILURES    → PRACTICE_PARTIAL
           │                                       │
           │                                       ▼
           │                                   KNOWLEDGE → KNOWLEDGE_DONE
           │                                                     │
           └─────────────── REPEAT_CYCLE ◀───────────────────────┘
```

Возникает вопрос: **нужен ли лимит** на количество циклов?

Варианты:

1. **Жёсткий лимит.** После N циклов — принудительный FINISH с пометкой
   «не сдал». Защита от бесконечного цикла.
2. **Мягкий лимит.** После N циклов — предупреждение, но продолжение
   возможно.
3. **Без лимитов.** Цикл идёт, пока сотрудник не зачистит зоны или не
   выйдет вручную (`BACK_TO_WELCOME` после Коммита 2).

## Решение

Принят **вариант 3**: лимитов нет. Поле `cycle_count` инкрементируется
при `REPEAT_CYCLE`, но **не используется** для блокировки переходов.

## Обоснование

1. **Цель тренажёра — обучить, а не отсеять.** Жёсткий лимит создаёт
   сценарий «не сдал, обращайся к руководителю», который противоречит
   self-paced формату обучения.
2. **Сотрудник может выйти сам.** Через `BACK_TO_WELCOME` (Коммит 2)
   из любого активного состояния. Принудительная остановка не нужна.
3. **`cycle_count` сохраняется как метрика.** Полезно для аналитики:
   «средний сотрудник проходит за 1.3 цикла», «топ-10% сложных
   продуктов — где cycle_count > 3». Это данные, не управляющий сигнал.
4. **Простота FSM.** Отсутствие guards по `cycle_count` упрощает таблицу
   переходов и тесты.

## Последствия

* `cycle_count` в `SessionContext` — счётчик-наблюдатель, не контроллер.
* Никаких guards вида `if ctx.cycle_count >= MAX_CYCLES`.
* Если в будущем потребуется лимит — это будет отдельный ADR с явной
  бизнес-мотивацией и новый guard в `FSMService`.

## Альтернативы

Вариант 1 (жёсткий лимит) рассматривался. Отвергнут как противоречащий
формату обучения и создающий тупиковый UX («что мне делать дальше, если
я не сдал?»).

Вариант 2 (мягкий лимит) — компромисс, но не решает проблему: если
предупреждение игнорируется и цикл продолжается, лимит превращается в
шум.
