# ADR-007: SessionRunner как координатор; эффекты — пустые намерения

* **Статус:** Принято
* **Дата:** 2025-XX-XX
* **Контекст:** Срез 2, проектирование слоя персистентности.

## Контекст

В Срезе 1 `FSMService.handle()` — чистая функция от `(state, command,
ctx)`, возвращающая `FSMResult(new_state, new_ctx, effects)`. Эффект
`PersistSession()` — пустой dataclass-маркер.

Перед Срезом 2 встал вопрос: **где** хранится `session_id` и **кто**
связывает результат `handle()` с конкретной сессией в БД.

Варианты:

1. **Эффект с данными.** `PersistSession(session_id, state, ctx)` —
   эффект самодостаточен, тонкий раннер просто вызывает store.save
   с тем, что лежит в эффекте.
2. **Тонкий координатор.** `PersistSession()` остаётся пустым
   маркером. Над FSM появляется слой `SessionRunner`, который держит
   `session_id`, вызывает `fsm.handle()`, и при наличии
   `PersistSession()` в effects — записывает `(session_id,
   result.new_state, result.new_ctx)` в стор.
3. **Без эффекта.** Персист — инвариант системы, координатор пишет
   всегда, без явного сигнала из FSM.

## Решение

Принят **вариант 2**: тонкий координатор `SessionRunner`.
```
infrastructure / web → SessionRunner → FSMService (pure)
↘ SessionStore (async I/O)
```


`SessionRunner.dispatch(session_id, command)`:

1. `snapshot = await store.load(session_id)`.
2. `result = fsm.handle(snapshot.state, command, snapshot.ctx)`.
3. Прогон `result.effects`: при `PersistSession()` →
   `await store.save(session_id, result.new_state, result.new_ctx)`.
4. Возврат `result` вызывающему слою.

`PersistSession` остаётся пустым frozen dataclass.

## Обоснование

1. **FSM остаётся чистой.** Никаких изменений в `domain/`,
   `application/effects.py`, `application/fsm_service.py`.
   Тесты Среза 1 (~150 шт.) не затрагиваются.
2. **Эффекты — намерения, исполнение — снаружи.** Это согласуется с
   ADR-004 («LLM-вердикт как факт»): домен описывает «что должно
   произойти», слой выше описывает «как именно». Эффекты типа
   `EvaluateDialog`, `GenerateReply` (Срез 3) встроятся в ту же
   модель.
3. **session_id — операционный идентификатор, а не доменный.** Контекст
   FSM (`SessionContext`) — часть домена: это агрегат состояния, на
   котором FSM принимает решения. А `session_id` — чисто
   инфраструктурный ключ для адресации в хранилище: домен про него
   не знает, FSM-функция его не получает и не возвращает. Живёт он
   там же, где живёт I/O — в координаторе и в БД.
4. **Симметрия с будущими эффектами.** Все эффекты будут пустыми или
   payload-несущими в зависимости от того, нужны ли исполнителю
   данные **сверх** того, что уже есть в `FSMResult`. Для
   `PersistSession` данные есть в результате — эффект пуст.

## Последствия

* Появляется новый класс `application/session_runner.py` (Коммит 8).
* Координатор знает структуру `FSMResult` — это нормально, он живёт
  слоем выше FSM.
* В Срезе 1 ничего не меняется.
* В Срезе 3 другие эффекты (`EvaluateDialog`, `GenerateReply`) будут
  встраиваться в `SessionRunner` по тому же принципу: проверка типа
  эффекта → вызов соответствующего исполнителя.

## Альтернативы

**Вариант 1 (эффект с данными)** отвергнут: требует менять
`PersistSession` и переписывать ~50 мест в тестах Среза 1, при этом
не даёт выгоды — координатор всё равно нужен (хотя бы как
точка входа из HTTP-слоя).

**Вариант 3 (без эффекта)** отвергнут: явный эффект — это документация
инварианта прямо в результате `handle()`. Полезно для отладки, логов,
будущей трассировки. Стоимость пустого dataclass нулевая.
