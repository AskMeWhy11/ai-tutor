# ADR-012 — TTS как эффект-конвейер аватара

## Статус
Принято.

## Контекст

В Срезе 1 у системы появляется требование озвучивать реплики
AI-аватара через SaluteSpeech (TTS). Реплики порождаются после
каждого перехода FSM и привязаны к новому состоянию.

Нужно решить:

1. Где синтезируется речь — на бэке или на фронте?
2. Как реплика аватара попадает в HTTP-ответ, чтобы FSMService
   остался чистым?
3. Что делать, если TTS недоступен (нет ключей, сетевая ошибка)?
4. Как сократить расход API SaluteSpeech на повторных репликах?

## Решение

**1. TTS — на бэке.** Это единственное место, где живут
креденшелы и доверенный CA-bundle Минцифры. Фронт получает готовый
URL и тег `<audio>`.

**2. Реплика аватара — это пара эффектов после persist.**
`SessionRunner` после исполнения `PersistSession` вызывает
`Avatar.next_message(new_state, new_ctx)` и порождает:

- `EmitText(text)` — всегда, если у аватара есть что сказать;
- `PlayAudio(url, mime)` — только если `TTSClient.synthesize` вернул
  байты, которые удалось сложить в кэш.

`FSMService` про озвучку не знает: он остаётся чистой синхронной
функцией. Цепочка эффектов выстраивается в координаторе
(`application/session_runner.py`).

**3. TTS-недоступность ≠ ошибка.** `TTSClient.synthesize` возвращает
`bytes | None`. Любая исключительная ситуация в реализации
(нет токена, 5xx, таймаут, отключено настройкой) логируется и
конвертируется в `None`. UI получает только `EmitText`, и сценарий
обучения продолжается.

**4. Кэш — файловый, ключ = sha256(audio_bytes).** Реплики
детерминированы (`StubAvatar` на конкретном `(state, ctx)` всегда
возвращает один и тот же текст), поэтому хеш по содержимому даёт
естественную дедупликацию. Кэш живёт в `var/tts/` (настраивается
через `TTS_CACHE_DIR`). Эндпоинт `GET /api/audio/{key}` отдаёт файл
с защитой от path traversal.

## Последствия

**Плюсы:**
- FSMService и domain не знают про TTS.
- Замена SaluteSpeech на другой движок — переписать один класс
  в `infrastructure/tts/`.
- Тесты `SessionRunner` подменяют `TTSClient` фейком и проверяют
  состав эффектов.
- Без креденшелов всё работает — просто без звука.

**Минусы:**
- Эффекты `EmitText` и `PlayAudio` не порождаются `FSMService`,
  а добавляются `SessionRunner`. Это исключение из правила
  «эффекты — это намерения домена», но оправдано: реплика аватара —
  свойство нового состояния, а не команды, которая в него привела.
- Кэш на диске. Для prod-деплоя на VPS этого достаточно;
  для k8s потребуется shared volume или замена реализации.

## Альтернативы

**A. TTS на фронте через Web Speech API.** Качество голоса хуже,
кириллица в браузерах звучит плохо, голос не SaluteSpeech. Отклонено.

**B. Сделать TTS обычным эффектом, который эмитится FSMService.**
Тогда сервису пришлось бы знать про существование аватара. Отклонено:
ломает чистоту FSM.

**C. Отдавать base64-аудио прямо в JSON-ответе.** Раздувает payload
в 1.3× и блокирует кэширование на стороне браузера. Отклонено.
