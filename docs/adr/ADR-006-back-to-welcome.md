# ADR-006: Возврат в WELCOME через EXIT_WARNING-состояния

* **Статус:** Принято
* **Дата:** 2025-04-27
* **Контекст:** Срез 1, проектирование UX-жеста «вернуться к выбору режима».

## Контекст

Сотрудник может захотеть **вернуться в меню выбора режима** (`WELCOME`)
из любой точки прохождения. Сценарии:

* «Я уже посмотрел теорию, хочу пропустить квиз и сразу пойти в практику».
* «Я начал EXAMPLE, передумал, хочу вернуться к выбору».
* «Я в KNOWLEDGE, но хочу заново посмотреть теорию по другой подтеме».

Текущая FSM (до Коммита 2) **не имеет** переходов в `WELCOME` из
основного потока. Возврат возможен только через `WARNING_DECLINED`
из `SKIP_WARNING_*` — это узкий случай.

Возникают подвопросы:

* Из каких состояний разрешён возврат?
* Нужно ли предупреждение о потере прогресса?
* Что считается «прогрессом» в коде FSM?
* Как реализовать механизм «возврат в исходное состояние при отказе»?

## Решение

Принята следующая схема:

### 1. Возврат разрешён из всех «продвинутых» состояний

Безопасные промежуточные (`*_DONE`) — **без предупреждения**:

| Из | Через | В |
|---|---|---|
| `TRAINING_DONE` | `BACK_TO_WELCOME` | `WELCOME` |
| `EXAMPLE_DONE` | `BACK_TO_WELCOME` | `WELCOME` |
| `KNOWLEDGE_DONE` | `BACK_TO_WELCOME` | `WELCOME` |

Активные блоки (`TRAINING`, `TRAINING_QUIZ`, `EXAMPLE`, `PRACTICE`,
`KNOWLEDGE`) — **через EXIT_WARNING**:

```text
<active>          ─BACK_TO_WELCOME─→ EXIT_WARNING_<active>
EXIT_WARNING_*    ─EXIT_CONFIRMED ─→ WELCOME
EXIT_WARNING_*    ─EXIT_DECLINED  ─→ <active>  (исходное)
```

### 2. Пять отдельных EXIT_WARNING-состояний (а не одно общее)

Альтернатива — одно общее `EXIT_WARNING` + поле `exit_warning_origin` в
контексте. Отвергнута: ломает принцип «FSM — чистая таблица»,
динамический возврат не описывается в `TRANSITIONS`.

Принятый вариант: **5 отдельных состояний**, каждое знает свой возврат
по таблице. Это симметрично с `SKIP_WARNING_1/2`, не требует доп. полей
в контексте, легко покрывается параметризованными тестами.

### 3. Контекст при `EXIT_CONFIRMED`

Возврат в WELCOME — **навигация, не сброс**. Контекст в основном
сохраняется. Исключение — поля «прогресса внутри блока»:

| Поле | Поведение при `EXIT_CONFIRMED` |
|---|---|
| `completed_modes` | Сохраняется. |
| `weak_zones_remaining` | Сохраняется. |
| `cycle_count` | Сохраняется. |
| `quiz_question_index` | Сбрасывается в `0` (только при выходе из `EXIT_WARNING_QUIZ`). |
| `last_answer_correct` | Сбрасывается в `None` (только при выходе из `EXIT_WARNING_QUIZ`). |

Логика: `quiz_question_index` и `last_answer_correct` — состояние
**внутри** квиза. После выхода квиз начинается заново при следующем
входе в `TRAINING_QUIZ`.

### 4. Команды и события

Новые команды:

```python
@dataclass(frozen=True)
class BackToWelcome:
    """Жест «вернуться к выбору режима»."""

@dataclass(frozen=True)
class ConfirmExitWarning:
    """Ответ на EXIT_WARNING_*: True = выйти, False = вернуться."""
    accept: bool
```

Новые события:

* `BACK_TO_WELCOME` — из любого «возврат-разрешённого» состояния.
* `EXIT_CONFIRMED` — пользователь подтвердил выход.
* `EXIT_DECLINED` — пользователь отказался.

## Обоснование

1. **Симметрия с `SKIP_WARNING_1/2`.** Та же модель: вход в warning →
   accept/decline → возврат или дальше.
2. **FSM остаётся чистой таблицей.** Никакого `origin` в контексте,
   никаких динамических переходов.
3. **`*_DONE`-состояния не нуждаются в предупреждении** — там
   «прогресс блока» уже зафиксирован в `completed_modes`.
4. **Активные блоки нуждаются в предупреждении** — там есть несохранённая
   работа (текущий вопрос, текущий диалог).

## Последствия

* FSM растёт с 16 состояний до **21**, с 28 переходов до **46**.
* `FSMService` получает новый обработчик `_handle_back_to_welcome`,
  табличный (маппинг активных состояний на их EXIT_WARNING).
* Тесты дополняются параметризованными случаями по 5 парам
  `(active_state, exit_warning_state)`.

## Что **не** входит в этот ADR

* Кнопка «Завершить обучение» из любого состояния — это другой жест,
  ведёт в `FINISH` напрямую, не через `WELCOME`. Скоп будущего ADR.
* Прерывание сессии по таймауту / закрытию бота — это уровень транспорта,
  не FSM.

## Альтернативы

* **Вариант: одно общее `EXIT_WARNING` + `exit_warning_origin` в ctx.**
  Меньше состояний (17 вместо 21), но усложняет контекст и нарушает
  «чистую таблицу». Отвергнут.
* **Вариант: возврат отовсюду без предупреждения.** Простой, но ломает
  UX — пользователь может случайно потерять прогресс квиза.
* **Вариант: возврат только из `*_DONE`.** Минимальный скоп, но не
  покрывает реальные сценарии («я в EXAMPLE, передумал»).
