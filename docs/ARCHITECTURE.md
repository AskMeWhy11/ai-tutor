# Архитектура

Документ описывает слои бэкенда и правила взаимодействия между ними.
По мере развития проекта документ детализируется (API, БД, фронтенд —
отдельными разделами или отдельными документами).

## Принципы

1. **Слоистая архитектура.** Зависимости направлены внутрь:
   infrastructure → application → domain.
   Domain не знает ни про что снаружи. Application не знает про
   фреймворки и I/O.

2. **Async только в infrastructure.** Domain и application — синхронны.
   Это упрощает тестирование и рассуждения о коде.

3. **Эффекты как данные.** FSMService возвращает побочные эффекты
   как структуры данных, не как вызовы. Исполнение эффектов —
   обязанность infrastructure.

4. **FSMService — единая точка диспетчеризации.** Не используем
   паттерн use cases (по одному классу на действие): для FSM
   из ~15 событий это даёт дублирование без пользы.

5. **Composition root.** Сборка приложения (DI) — в одном месте,
   `composition/`. Никаких глобальных синглтонов.

## Слои

```
src/
├── domain/             # Чистая бизнес-логика. Без I/O, async, фреймворков.
├── application/        # Оркестрация FSM. Синхронно.
├── infrastructure/     # Адаптеры к внешнему миру. Async здесь.
└── composition/        # Сборка приложения, точка входа.
```

### `domain/`

Содержит:
- `states.py` — перечисление состояний FSM.
- `events.py` — перечисление событий FSM.
- `transitions.py` — таблица переходов и функция `get_next_state`.
- `context.py` — `SessionContext`: данные сессии, не зависящие от состояния.

Правила:
- Никаких импортов из других слоёв.
- Никаких I/O, async, БД, HTTP, LLM.
- Только `dataclasses`, `enum`, чистые функции.
- Должен компилироваться и тестироваться без установленных
  fastapi/sqlalchemy/etc.

### `application/`

Содержит:
- `commands.py` — команды от внешнего мира (`StartBot`, `SubmitQuizAnswer`,
  `PracticeEvaluated`, `BackToWelcome` и т. п.).
- `effects.py` — эффекты, которые FSMService просит исполнить
  (`EmitMessage`, `PersistSession`, `EvaluateDialog` и т. п.).
- `fsm_service.py` — `FSMService.handle(command, ctx, state) → (new_state, new_ctx, [effects])`.

Правила:
- Может импортировать из `domain/`.
- Не импортирует из `infrastructure/`.
- Синхронный код. Никаких `async def`, никаких `await`.
- Не делает I/O. Не вызывает LLM. Не пишет в БД.
- Все побочные эффекты возвращает наружу как `effects`.

Команды несут **факты**, а не сырые данные для последующей обработки.
Например, `SubmitQuizAnswer(correct: bool)`, а не `SubmitAnswer(text: str)`:
вердикт LLM вычисляется на слое выше и попадает в FSM как готовое
решение. Подробнее — [ADR-004](docs/adr/ADR-004-llm-verdict-as-fact.md).

### `infrastructure/`

Будет содержать (по мере появления срезов):
- `persistence/` — SessionStore, репозитории, SQLAlchemy-модели.
- `llm/` — клиент GigaChat (и заглушка для тестов).
- `speech/` — клиент SaluteSpeech.
- `web/` — FastAPI-приложение, роутеры, схемы.
- `prompts/` — хранилище промптов.

Правила:
- Может импортировать из `domain/` и `application/`.
- Async-код живёт здесь.
- Реализует интерфейсы (Protocol), объявленные в `application/`
  или собственные внутри `infrastructure/`.
- Исполняет эффекты, которые вернул FSMService.

### `composition/`

Содержит фабрику приложения: создаёт инстансы адаптеров,
прокидывает зависимости, регистрирует роутеры.

## Поток управления (общий вид)

```
HTTP-запрос
   ↓
infrastructure/web (роутер)
   ↓ (десериализация → Command)
application.FSMService.handle(command, ctx, state)
   ↓ (новый state, новый ctx, [effects])
infrastructure/web (исполнение эффектов через адаптеры)
   ↓
HTTP-ответ
```

Никаких прямых вызовов LLM или БД из application. FSMService говорит
«мне нужно вычислить ответ LLM по этому промпту», возвращая эффект
`AskLLM(prompt=...)`. Веб-адаптер вызывает `LLMClient.ask(prompt)`,
получает ответ, и формирует следующую команду в FSMService
(или сразу отвечает клиенту, если этого достаточно).

Точная схема исполнения эффектов оформится на Срезе 3, когда появятся
первые «настоящие» эффекты с LLM. До этого — только синхронные эффекты
типа `PersistSession`, исполняемые в одну строчку.

## FSM и контекст

FSM управляет порядком прохождения сценария обучения. Она знает
«какое сейчас состояние», «что произошло», «куда переходить» — но
не знает про тексты сообщений, содержимое теории, промпты LLM или
транспорт.

Подробная документация:

- [`docs/FSM_DESIGN.md`](docs/FSM_DESIGN.md) — полная структура FSM:
  состояния, события, таблица переходов, Mermaid-диаграмма.
- [`docs/FSM_INVARIANTS.md`](docs/FSM_INVARIANTS.md) — правила мутации
  `SessionContext`: какое событие меняет какие поля.

Ключевые архитектурные решения:

- [ADR-004](docs/adr/ADR-004-llm-verdict-as-fact.md) — LLM-вердикт
  попадает в FSM как факт через команду, FSMService не вызывает LLM.
- [ADR-005](docs/adr/ADR-005-no-cycle-limits.md) — петля ремедиации
  без лимитов; `cycle_count` — метрика-наблюдатель, не контроллер.
- [ADR-006](docs/adr/ADR-006-back-to-welcome.md) — возврат в WELCOME
  через 5 EXIT_WARNING-состояний с подтверждением.

Базовые свойства FSM:

- **Чистая таблица переходов.** Целевое состояние получается из
  `(state, event)` без чтения контекста. Контекст влияет только на
  выбор события (guards в FSMService), не на исход перехода.
- **Контекст мутируется только в FSMService.** Домен не знает про
  контекст. Все мутации привязаны к конкретным событиям и описаны
  в `FSM_INVARIANTS.md`.
- **Никаких асинхронных вызовов внутри FSM.** Если нужен внешний
  ответ (LLM, БД) — это эффект или факт, поступающий следующей
  командой.

## Тестирование

- `domain/` и `application/` — unit-тесты, в памяти, без зависимостей.
- `infrastructure/` — unit + integration. Integration требуют запущенного
  PostgreSQL (через docker compose).
- End-to-end сценарии — отдельная директория `tests/e2e/`,
  собирают приложение целиком с фейковыми внешними сервисами.
